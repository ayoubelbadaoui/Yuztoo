## MAJOR

### [MRN-04] currentMerchantForOwnerProvider turns any load failure into 'no merchant' and keeps it forever (keepAlive)
- **Where:** `lib/feature/merchant/application/providers.dart:136` · group merchant-rappels-notifications · verdict **confirmed** · onboarding · Crashlytics: cloud_firestore/unavailable on documentReferenceGet
- **Scenario:** The provider swallows both a Left from getMerchantById (offline, cloud_firestore/unavailable, permission-denied) and thrown errors and returns null, and calls ref.keepAlive(). A merchant opening the app on a bad network gets null, which every screen interprets as 'no merchant profile' (Rappels shows nothing, settings skeleton forever, routing may offer merchant onboarding again, hasLinkedMerchantAccountProvider falls through). The null is cached until something invalidates it manually. Matches the cloud_firestore/unavailable on documentReferenceGet signals.
- **Fix:** Throw (AsyncError) on Left/exception so UIs can show a retry state, or at minimum do not cache a failed load: call ref.invalidateSelf() after a delay / skip keepAlive on failure.
- **Verifier:** providers.dart folds Left to null, catches throws and returns null, and calls ref.keepAlive(), so the null is cached until invalidated. A getMerchantById failure while offline is treated as no merchant.

### [MRN-05] Merchant settings shows the loading skeleton forever when the merchant is null/failed
- **Where:** `lib/feature/merchant_settings/presentation/merchant_settings_screen.part.dart:19` · group merchant-rappels-notifications · verdict **confirmed**
- **Scenario:** isLoading = !_initialised, and _seed is only called when currentMerchantForOwnerProvider yields a non-null merchant. If the load failed (see MRN-04), the merchant is missing, or the user has no store yet, the screen shows the skeleton indefinitely with no retry and no logout button (logout is inside _buildContent). Pull-to-refresh is also unavailable on the skeleton.
- **Fix:** Derive loading from merchantAsync.isLoading; render content (with defaults) or an error/retry state when the value is null, and always expose logout.
- **Verifier:** isLoading = !_initialised, and _seed only runs for a non-null merchant. With a null merchant the skeleton stays forever. The pull-to-refresh and logout button are inside _buildContent, so neither is reachable.

### [MRN-06] Identity form is seeded before user profile loads, leaving first/last name and DOB empty (and owner email never seeded)
- **Where:** `lib/feature/merchant_settings/presentation/merchant_identity_edit_screen.dart:186` · group merchant-rappels-notifications · verdict **confirmed**

- **Verifier:** _seed runs on every build and sets _seeded=true as soon as basics or merchant is non-null. When the merchant is already resolved and basics are still loading, it seeds empty first name, last name and DOB. The spinner gate does not stop the seed, and the fields are never refilled. _ownerEmailCtrl is never assigned from anything. Save then sends lastName null, dateOfBirth null and ownerEmail null.

### [MRN-11] Notification create rule lets any signed-in user inject notifications into any other user's inbox when merchant_id is empty or absent
- **Where:** `firestore.rules:209` · group merchant-rappels-notifications · verdict **confirmed**
- **Scenario:** allow create on users/{userId}/notifications is true when `!('merchant_id' in data) || data.merchant_id == ''`. The Flutter client always sends merchant_id (possibly ''), and the Cloud Function onNotificationCreated pushes an FCM for each doc. Any authenticated account can write arbitrary title/body notifications (spam, phishing text with a fake merchant_name) to every user's inbox and trigger real pushes. The comment above the rule claims it blocks exactly this impersonation.
- **Fix:** Remove the empty/absent merchant_id branch for non-owners (system notifications should be written by Cloud Functions with admin SDK), or require canManageStore for any create where userId != auth.uid; also restrict allowed keys/types and length of title/body.
- **Verifier:** The rule allows create when the user is signed in and (isOwner || merchant_id is absent || merchant_id == '' || canManageStore). Any signed-in user can therefore write to another user's inbox with an empty merchant_id. This is a real security hole that contradicts the comment above the rule.

### [F1] Account purge deletes whatever merchant the client-writable users.merchant_id points to
- **Where:** `functions/src/index.ts:2659` · group core-org-backend-native · verdict **confirmed**
- **Scenario:** firestore.rules lets a user write any value to users/{uid}.merchant_id: the update rule only checks status, onboarding and roles. A malicious or buggy client sets merchant_id to another shop's doc id, then calls purgeAccount, or its account is purged by the soft-delete sweep. cascadeEraseUserData does deleteStoragePrefix('merchants/<victim>') and recursiveDelete(merchants/<victim>) with no check that merchants/<victim>.owner_uid == uid. The comment says 'if owned', but the code does not check. purgeExpiredUsers and onAuthUserDeleted reuse the same cascade. The same user doc also supplies email and phone, which are used as knownDocId in deleteIndexDocsForUid, so another user's email_index or phone_index entry can be deleted without checking its uid.
- **Fix:** In cascadeEraseUserData, load merchants where owner_uid == uid and only delete those. Before deleting a known email_index or phone_index doc, verify its uid field equals the caller. Also add a rule so users.merchant_id can only be set to a merchant whose owner_uid is the writer or to which the user has a store role.
- **Verifier:** The users update rule only blocks the admin-owned fields (deleted_*, created_by_admin). merchant_id is client-writable. cascadeEraseUserData reads users.merchant_id and recursiveDeletes merchants/<id> and its Storage prefix with no owner_uid check. email and phone feed deleteIndexDocsForUid as knownDocId with no uid check.

### [F2] Any signed-in user can inject notifications and pushes into another user's inbox
- **Where:** `firestore.rules:207` · group core-org-backend-native · verdict **confirmed** · Crashlytics: cloud_firestore/permission-denied in recordSentNotificationOpen (related area)
- **Scenario:** The create rule for users/{userId}/notifications permits any signed-in user when merchant_id is absent or empty. An attacker writes {title, body, type} into a victim's inbox. The onNotificationCreated trigger (index.ts:844) then sends an FCM push to the victim using the attacker's title and body: a phishing and spam vector with Yuztoo branding.

- **Verifier:** The create rule on users/{uid}/notifications allows any signed-in user when merchant_id is absent or empty. The inbox write and the FCM push that follows it are attacker-controlled.

### [F7] Adding or removing a connected city overwrites the list with [] when the provider is loading or errored
- **Where:** `lib/feature/account_preferences/presentation/widgets/cities_section.dart:174` · group core-org-backend-native · verdict **confirmed** · onboarding
- **Scenario:** build shows [] while connectedCitiesProvider is loading or in error. _buildAddButton and _removeCity read `ref.read(connectedCitiesProvider(uid)).value ?? ### [MRN-02] Onboarding always writes merchants/{uid} with set(merge:false): a retry or double submit overwrites an existing store
- **Where:** `lib/feature/merchant/infrastructure/firestore_merchant_repository.core.part.dart:77` · group merchant-rappels-notifications · verdict **plausible** · onboarding
- **Scenario:** CompleteMerchantOnboarding builds Merchant(id: userId) and createMerchantAndLinkUser does batch.set(merchantRef, dto.toFirestore(), SetOptions(merge:false)). ### [F16] Scheduled notification retry loop can re-send the same notification repeatedly
- **Where:** `functions/src/index.ts:2526` · group core-org-backend-native · verdict **plausible**
- **Scenario:** processScheduledNotifications claims a doc as 'processing', writes one notification doc per follower, then runs the quota transaction and finally sets status 'sent'. If anything after the fan-out throws (quota transaction contention, doc.ref.update failure), the catch block flips the doc back to 'pending'. ### [LQB-02] No serialization of peripheral/scan start-stop; shell and BLE screens fight over the same radio on resume
- **Where:** `lib/core/infrastructure/ble_proximity_notifier.dart:140` · group loyalty-qr-ble-crm · verdict **unverified** · onboarding · Crashlytics: iOS BLE 'Service addition timed out'
- **Scenario:** startAsClient/startAsMerchant/_stopInternal/resume*/suspend* are plain async methods without a mutex. Quick inactive->resumed cycles run two overlapping startClientBroadcast calls on the BlePeripheral singleton, so one call's clearServices/stopAdvertising lands in the middle of the other's addService and the serviceAdded callback never fires (5 s timeout).
